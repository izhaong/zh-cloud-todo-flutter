## 需求与裁定

1. **「+」是独立的拖出载荷，不复用 `TodoTask`。** 新增 `QuickAddSubtaskIntent`：
   它不代表某个已存在的任务，只代表"要建一个子任务"。用独立类型而不是共用 `TodoTask`，
   是因为 SDK 找落点时先按泛型过滤拖拽数据 ⇒ 同一块右下象限里可以叠两个 `DragTarget`，
   各吃各的拖，不必为「+」再划一块区域，也不会互相截走
   （复算 `git grep -l "DragTarget<QuickAddSubtaskIntent>" origin/develop -- lib` ⇒ 只列出一个文件，
   落点实现在这一处；`-l` 数的是文件，别与数行的 `-c` 混用）。
2. **落点、闸门、象限与 `specs/113` 共用同一份。** 「+」那一层嵌在右下象限的 `DragTarget<TodoTask>`
   里面，`enabled`（页身份 + `TodoLists.writable`）判一次就够；正反用例两边各有（智能清单、只读清单）。
3. **点开的是同一张表、同一个入口。** 页面把落点回调接到 `addSubtaskFlow`（详情层与右键那档用的就是它），
   所以深度 ≤5 的守卫与那句提示在 `lib` 里仍只有一份（复算
   `git grep -c 已达最大嵌套层数 origin/develop -- lib` ⇒ 一个文件命中一次；本轮新增的"入口抛错要看得见"
   用例正是拿这句中文当断言的）。
4. **点击通道不能被拖拽层吃掉。** `Draggable` 的 pan 识别器只在有位移时赢手势竞技场，
   不产生位移的点击仍归 `FloatingActionButton`。既有 `test/features/shell/quick_add_hash_tag_test.dart`
   与 `test/features/shell/quick_add_bar_test.dart` 都在点这个「+」（本轮一字未改仍过），
   本面另加一条"点它建出来的是顶层任务（`parentTaskId` 为空）"把点与拖的**结果差异**也钉住。
5. **两条 `Positioned.fill` 不是修饰。** `Stack` 给非 positioned 子节点的是 loose 约束：
   高亮与内层落点按内容收缩就变成 0×0 —— 0 尺寸既画不出高亮，也进不了命中路径
   （`DragTarget` 的盒子只在 `size.contains(position)` 时挂进路径）。这条是三条用例先全红才定位到的。
6. **失败必须看得见**：建表入口抛错时走 `describeError` 上屏（与上一面同一条仓内不变量：
   把异常对象直接插进文案会被 `test/tooling/raw_error_text_gate_test.dart` 判失项）。

## 对 `specs/113` 的更正（就地改，不改结论状态）

`specs/113-subtask-drop-zone/spec.md` 的「形态差额」一节记了两条：
"拖出源是整行长按而非任务前的图标" 与 "落到左半不换位置"。本轮实测第一条**不成立**：
用例「长按落在行最前的图标/勾选区也起拖」（`test/features/task/task_subtask_drag_test.dart`）
从行首 14px 那条起拖并落到另一行右下 ⇒ `parentTaskId` 写进去，
而《01-列表视图.md》`:49` 原文写的就是「长按任务」⇒ 整行长按是原文的形状，不是偏离。
第二条成立且已立 FL #595。⇒ 该节已就地改写为"一条差额 + 指向 #595"，
矩阵 #23 的说明格随之更正（`有 27 / 部分 40 / 无 11 / 范围外 11` 四个数与缺口 51 都不动，理由见下）。

## 矩阵 #23 为什么仍「部分」

本面把 `:24` 交付掉之后，这一行还剩两处有据可查的不足，**都不在本轮范围内**：

1. 清单页只渲染顶层任务（`watchTopLevelByList`），子任务不作为行 ⇒ 拖完这一行从列表消失，
   "每一个层级的子任务在功能上都与普通任务相同"这句在清单页看不见；`specs/032` T013 已把子任务树单列。
2. 「长按任务、自由选择放置位置」的排序落点未做 ⇒ FL #595。
