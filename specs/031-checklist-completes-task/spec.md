# 031 · 检查事项全部完成驱动主任务完成（嘀嗒对照矩阵 #23 / #8）

**状态：** 已实现待合并（本地六项门禁全绿；矩阵 #23 行状态只在 PR 合并后翻）
**依据：** `zh-cloud-docs/todo/99_参考资料/dida365-help-center/02-功能指南/01-任务/08-如何管理海量任务/06-多级任务.md:176-179`
**范围：** 只补「检查事项 → 主任务完成」这一条驱动关系。多级子任务的取数与五级约束已在 `specs/007` 落地，本规格不重做。

## 可验证行为

1. 一个任务的检查事项**全部为已完成**且这次动作是把某条勾成完成时，该任务本身被标记完成（`completed=true`、`completedAt` 非空），并**恰好**写一条 `entity=task / op=upsert` 的 outbox，载荷 `status=DONE`、`completedAt` 非空。（不写「`updatedAt` 前进」这条断言：SQLite 以毫秒存时间，同一轮内 `created→auto-complete` 可能同毫秒，断言会 flaky，改由 `completedAt` 与 outbox 作证。）
2. 仍有未勾完的检查事项时：任务状态不动，也不写属于该任务的 outbox（只写被勾那条检查事项自己的）。
3. 反向取消一条检查事项**不会**把任务改回未完成，也不追加任务 outbox。
4. 任务此前已是完成态（用户手动勾选或上次自动完成）时，再补齐检查事项不重复入队。
5. 已作废（`cancelled`，回收站）的任务不因勾选项被"复活"。
6. 规则只由"勾选完成"这一条路径触发：该路径下被勾的项必属本任务，所以不存在"零条检查事项被判定为全部完成"的入口（`deleteChecklistItem` 本轮未接线，见仍缺）。
7. **子任务完成不影响父任务的完成状态**（嘀嗒：只有检查事项驱动进度）；同清单的兄弟任务互不受影响。
8. 详情面板勾完最后一条检查事项后，头部完成按钮由「勾选完成」变为「取消勾选」——即自动完成要经 `watchById` 流刷新到 UI，不是只写库。
9. **只读清单**（`todoLists.writable=false`，如共享只读）里勾满检查事项：勾选本身照常入库，但不替用户把父任务判完成，也不追加 `DONE` 出队。

## 取舍与被否方案

- **取消勾选不回退任务**（行为 3）：嘀嗒帮助页只写了"检查事项全部完成后主任务将自动完成"，没写反向。要做"只在自动完成时才回退"必须知道该完成是自动还是手动的，而 `todo_task` 没有这个标记列 ⇒ 加列属 SQL/契约变更（需授权 + Service 同步）。在两难里选**不反转**：把用户已认定完成的任务改回未完成，比保持状态更危险（可能连带撤销他们之后的操作）。
- **只挂 `toggleChecklistItem`，不挂 `deleteChecklistItem`**（保持单轮单门槛）：删掉唯一未勾项会留下"全部完成"的既成事实，嘀嗒口径下同样该自动完成，但那会让"删除末条待办"变成"完成整个任务"的隐式副作用，风险要单独评估。已在 `tasks.md` 记为仍缺，不静默宣称完成。
- **被否：把自动完成放在 UI 层**（`task_detail_pane._toggle` 里判断后再调 `toggleComplete`）— 批量导入、同步回灌、将来其它入口都绕过它，规则会漂。放在 repository 事务内才是唯一真相源。
- **被否：让 Service 计算并回灌完成态** — 现有 `/app-api/todo/**` 无该语义，且离线优先是本项目底座；纯本地规则不该等网络。
