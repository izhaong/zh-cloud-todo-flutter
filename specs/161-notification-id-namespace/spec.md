# 161 · OS 通知 id 的类型命名空间（原 FL #358 客户端切片）

## 病灶

客户端把服务端 `dispatch.id` **直接**当 `LocalNotificationService` 的 OS 通知 id 用。
「@ 提及」的通知一旦并入同一条流，两条流的 id 会在**同一个命名空间**里相撞 ⇒
后到的那条**顶掉前一条**（用户看到"一条通知变成了另一条"）。

这正是 opencode 交叉验证（#358）点名的："**唯一真正必须统一的：身份/去重键** ——
提及若另起 id 空间，必须加类型命名空间，否则两条流的通知 id 会在通知中心相撞。"

## 改动

1. **`todo_notification_id.dart`**：32 位 OS id 空间按类型切两个区间
   （提醒 `0x1000_0000` 起、提及 `0x2000_0000` 起），**跨类型永不相等**；
   超 20 位的服务端 id **取模**而不是抛错 —— 两条通知共用 id 是可接受的退化，
   抛错会让**整轮 poll 中断**，那才不可接受；
2. `ReminderNotificationPoller` 的 `schedule`/`show` 改走
   `reminderOsNotificationId(item.id)`；
3. **客户端通知 API**（`TodoNotificationApi`）：`GET /todo/notification/unread` +
   `PUT /read` —— **与提醒收件箱是两个端点**，故意不合并（那是提醒专用链路：
   按 `timeMode` 重解释触发时刻、把未来项交 OS 持久调度、文案写死「到期提醒」）。

## 判据

| 判据 | 说明 |
| --- | --- |
| **跨类型永不相等**：扫 5000 个编号，`reminder(id) != mention(id)` | 命名空间的意义本身 |
| 同类型内不同 id 仍不同 | 不因命名空间而塌缩 |
| 同 id 稳定 | 重排后仍是同一条通知 |
| 异常大 id **不抛错** | 抛错会让整轮调度失败 |
| **两条流是两套类型**（`ReminderInboxItem` ≠ `TodoNotificationItem`） | 提及不进提醒调度链的**结构前提** |

**反向探针**：把提及的 base 改成与提醒相同（= 没有命名空间，正是原来的撞车形态）
⇒ 「跨类型永不相等」**转红**。

## 顺带发现并落实的

**提及根本不该走提醒那条轮询链** —— 现在是**结构上不可能**：提醒收件箱与通知收件箱
是**两个端点、两个类型**，`ReminderNotificationPoller` 只读前者。
这条作为**结构判据**钉住（不是"我记得没接"，而是**两条流不共用入口**）。

## 边界（下一刀）

- **通知列表 UI**（客户端）：读 `TodoNotificationApi.unread` 渲染，提及点进评论；
- **提醒侧写时扇出**（service）：`SENT` 派发同步写一行 `REMINDER` 通知 —— 本切片未做；
- **清理策略**：评论/任务删除时通知跟着走，等形状稳定。
