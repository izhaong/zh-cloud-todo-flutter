# 067 · 任务与日历并列视图：拖动到清单或标签上（矩阵 #32 面 ③）

判据源：`zh-cloud-docs/todo/99_参考资料/dida365-help-center/02-功能指南/02-日历/07-任务与日历同时显示.md`

## 一、原文口径（术语照抄）

小节标题是 `:45`「拖动排期，让安排更高效」，`:47`「在任务与日历并列显示的视图中，你可以：」列出四条，
本面吃的是第三条：

- `:57`「拖动到清单或标签上：」
- `:59`「任务会被移动到目标清单，或自动打上相应标签。」

原文对这一条只给了两个动作与两个结果：**移动到目标清单** / **自动打上相应标签**。
它没有说这一条要动时间安排，也没有说落点只在并列视图里才成立。

同一小节里与本面相邻、但**不属于本面**的两条，划清边界免得串味：

- `:53`「将日历中的任务拖入清单详情区域」+ `:55`「任务会从原所属清单迁移到当前查看的清单中，并保留其原有的时间安排。」
  ⇒ 那是面 ②（FL Issue #398 / PR !406），落点是清单详情区域本身，目标清单是「当前查看的」那一个。
- `:61`「拖动到智能清单上」+ `:63`「会为任务自动添加该智能清单关联的时间条件，例如“今天”、“本周”等。」
  ⇒ 那是面 ④（FL Issue #400），本面不碰智能清单行。

## 二、面 ③ 的验收口径

1. **落点是侧栏的清单行与标签行**（`lib/features/shell/sidebar.dart` 的 `_ListRow` / `_TagRow`），
   载荷沿用既有的 `TodoTask` 拖出源：看板、时间线、并列视图的清单行都已经在拖这个类型。
2. **拖到清单行 = 移动到目标清单**：只写 `listId`；`sectionId` 属于原清单，换清单后必须一起清掉
   （留着它，任务会带着一个不属于新清单的分组 ID）。时间安排（`dueAt`/`startAt`/`endAt`）一毫秒不动 ——
   原文这条只提清单。
3. **拖到标签行 = 自动打上相应标签**：`tagIdsOf(taskId)` 读现值后**追加**，不覆盖已有标签；
   任务已经有该标签时不发写请求（去重挡在写之前，白登一条同步变更算缺陷）。
4. **同清单不落**：把任务拖回它自己所在的清单行，判定为 `skipped`，一次写都不发。
5. **同一任务连落两刀要串行**：后一刀必须等前一刀的写落完，不能插队；前一刀失败也要把链条续上，
   不能让后续写被旧错误静默吞掉。
6. **失败必须看得见**：写库抛错或仓储未就绪 ⇒ 侧栏所在 Scaffold 上给可见提示；
   提示只在同一次落点失败时出现，去重/原地不动都不弹。

## 三、契约与落点端

纯客户端：`todo_task` 的 `listId`/`sectionId` 与任务-标签关系都已在本地 Drift 与 `/app-api/todo` 契约里，
`TagRepository.setTaskTags` 也已存在 ⇒ 本轮不动 `zh-cloud-service`，落点端记 **FL**。

## 四、取舍（写下为什么是这样做，而不是别的样子）

- **写库走函数接缝（`moveTask` / `attachTag`），不把 `TaskRepository` 整个塞进控制器**：
  「不发写请求」「串行」「失败后链条不断」这三条要能被证伪。伪造整个仓储意味着
  每个用例都得先抄一遍 `update(...)` 的 17 个具名参数，测的就不是判据而是抄写。
- **读屏文案只在候选态给**（指针停在落点上才有 `Semantics(label:)`）：
  侧栏有几十行，静止态每行都挂「移入清单」等于给读屏用户制造噪声；
  行名本身的语义（`_SidebarRow` 的 label）不受影响。
- **不复用 PR !406 的 `TaskListMoveController`**：那个类落在 `lib/features/task/list_drop_target.dart`，
  只服务「移到当前查看的清单」。本面的目标清单是**被 drop 的那一行**，语义不同；
  更重要的是 !406 正在只读复核中，本分支去改它的文件会把 PASS 与字节的绑定打断。
  两处编排的重复（串行链）在 !406 合并后单独收口，不在本轮顺手做。
- **落点不挑视图**：原文 `:47` 的「在任务与日历并列显示的视图中」是这一节的场景描述，
  不是对落点的约束；侧栏清单行在任何视图下都是合法的「移动到目标清单」落点。
