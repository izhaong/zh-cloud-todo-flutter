# 056 任务档「固定时间」选择器（矩阵 #12 缺项 ⑤ / FL Issue #369）

## 判据源（逐字，zh-cloud-docs 镜像 `todo/99_参考资料/dida365-help-center/02-功能指南/01-任务/07-固定时间与固定时区.md`）

- `:11`「开启后，在为任务设置时间时，即可选择「固定时区」或「固定时间」。」
- `:31`「可以在任务「日期弹窗」-「时间」- 选择「固定时区」或者「固定时间」。」
- `:48`「选择「固定时区」，即意味着任务的时间会随着所在时区的不同而改变。」
  `:50` 示例 1「如果你从北京飞到莫斯科，那么北京时间上午 11 点的任务，将会显示为莫斯科时间上午 6 点。」
- `:60`「选择「固定时间」，即意味着不论所处时区如何变化，任务的时间都会保持一致。」
  `:64`「…滴答清单都会在当地时间上午 7 点提醒你早起运动。」

⇒ 三态：未选（浮动）／「固定时区」／「固定时间」。档位名照抄，不自创同义词。

## 契约（服务端已实现、未合并：zh-cloud-service Issue #290 → PR !291）

`time_mode` tinyint：`0` 浮动 / `1` 固定时区 / `2` 固定时间；`fixed_timezone` 是派生兼容位
（**只有 `1` 为 true）；两档固定都必须带 `time_zone`。本仓读写一律以 `time_mode` 为权威，
`fixedTimezone` 只作为给旧数据/旧调用方的推导值。

## 设计决定与取舍（拿不准的按推荐走，写在这是为了复核能驳）

1. **控件形状**：嘀嗒只有一个动词「选择」，页面截图取不到文字 ⇒ 无法确证它是分段控件还是单选列表。
   取**两个互斥选项 + 可全不选**（`RadioListTile` 组，`groupValue` 允许 null），
   因为这样只需要嘀嗒给过的两个词；若做成三档单选就得给它起个「不固定」的名字 —— 那是发明用词。
   **代价**：真实嘀嗒客户端可能是分段控件，视觉不完全一致；用词与语义一致。
2. **宿主位置**：沿用本面已有的时区块（`task_detail_pane.dart` 的提醒配置区），
   并与 specs/055 的「设置 → 日期与时间 → 时区」总开关同源 —— 嘀嗒 `:11` 写的是"开启后才可选"，
   所以总开关关着时这一组选项不出现。
   ⚠️ 前置 !370（总开关）**未合并**，本 PR 堆在它上面（stack），base 不是 develop。
3. **不改 9 张黄金基线**：新控件在弹窗/抽屉内，金样本拍的是 workspace 与详情面板本体；
   若门禁 4 变红说明这个假设错了，**停下请示**而不是重录。
4. **提醒侧不做**：`todo_reminder` 的 `timeMode` 接线在 service #292，本面只收任务档。
   ⇒ 会出现"任务已选固定时间、提醒仍按老位"的中间态，这是已知的、被两仓各自排期切开的代价。

## 验收标准（每条都要能复算）

- R1 存储：`todoTasks.timeMode` 落库、schemaVersion 递增、旧库升级后默认 0（浮动）。
- R2 出站：任务同步 payload 带 `timeMode`，且服务端字段名一致（`timeMode` / `time_mode` 两种写法都能被解析）。
- R3 语义：`1` 换算到用户时区显示；`2` 墙钟原样显示且标签用「固定时间」；`0` 与今日行为一致。
- R4 交互：两个选项互斥、可全不选；选中即写 `timeMode`，全不选写 `0`；
  只有「固定时区」这一档必须填 IANA（对齐服务端 `1_020_001_064` 的判据）。
- R5 四件套（新增界面必过）：320px + 1.3 倍字号在**该 sheet 自己的 context** 上实测不溢出；
  两个选项各有独立读屏语义；保存失败时保留已加载数据；过期响应不覆盖新响应。

## 实测后果（本轮跑出来的，不是推测）

门禁读数：`flutter analyze` ⇒ `No issues found!`；`flutter test --tags golden` ⇒ `+9 All tests passed`（
**没碰 9 张基线**，spec 决定 3 的假设成立）；
`flutter test --exclude-tags 'golden || performance' --concurrency=1` ⇒ `+901 ~26 -17`。

那 17 条红的**全部**叫得出名字：`固定时区…墙钟…`（日历落格、看板截止、时间线分桶、侧栏计数、
今日投影、详情渲染与回环、推荐任务入队…）。清单见 `tasks.md`。

⇒ 它们钉的是 develop 的旧语义：**「固定时区」＝按配置时区保留墙钟**。
而嘀嗒 `:48/:50` 给「固定时区」下的定义是"时间会随所在时区改变"（北京 11 点 → 莫斯科显示 6 点），
"保留墙钟"是 `:60/:64` 的「固定时间」。也就是说 develop 把两档做成了一档，
并且做成的是**贴着「固定时间」的行为、挂着「固定时区」的名字**。

本笔的实现按原文把两档拆开，于是这 17 条必然红。两种收法：

- **A（本笔走的路，推荐）**：照嘀嗒翻转「固定时区」的行为，17 条测试逐个改成
  "配置时区是锚点、显示随设备时区走"，另给「固定时间」补一组"墙钟不动"的测试。
  **代价要说清**：已有用户那些勾了「固定时区」的任务，在设备时区 ≠ 锚点区时
  **显示出来的钟点会变**（这正是一次缺陷修复的应有样子，但它是用户可见的变更）。
- B：保留行为、只把界面名字从「固定时区」改成「固定时间」，再另做真的「固定时区」。
  这样 17 条测试不用动，但 develop 上那一档从来不是嘀嗒说的「固定时区」，
  等于把缺陷改名为另一个功能，矩阵 #12 的 ③ 也得跟着下调。

B 看起来省事，但它把"标签与行为不一致"这个病根留着了，所以选 A。
**这一条要人过目**：A 会改用户已设任务的显示时刻，不是纯新增。

## 交叉验证后的改判：走 B（原推荐 A 被推翻）

`cursor-agent --trust` 独立评审的结论是 `CROSSCHECK: B`（输出 5,469 字节，原文存
`/tmp/cx/ab-out.md`），四条理由里有一条我此前完全没看到，且复验成立：

> 存量勾选对应的**行为**是墙钟保留，翻转成"绝对时刻 + 随设备时区换算"是改用户意图，
> 不是修显示 bug；`true→1` 等于把错名写进 `time_mode`。

我复验的路径是 develop 的实现本身：`task_time_formatter.dart` 对 `fixedTimezone=true`
走 `_fixedLocation` ⇒ 拿配置时区渲染，钟点**不随设备时区变** —— 这正是嘀嗒给「固定时间」
下的定义。也就是说名实不一致的是**标签**，不是行为。上一轮我把"以代码为准"错用成了
"以列注释与标签为准"，方向反了。

⇒ 本分支现在做的是 B：`fromLegacyFlag(true) → fixedTime`（2）、`legacyFlagOf` 为
"非浮动即 true"（保住老客户端读到的位不翻）、`task_repository` 里只给老位的调用方
按同一口径推档位（否则加列默认 0 会让存量行静默退成浮动）。另补了本地迁移回填
`UPDATE todo_tasks SET time_mode = 2 WHERE fixed_timezone = 1` —— 没有它，用户升级后
那些勾过的任务会当场丢行为，这条是我在跑测试时才撞出来的，service 侧同样要补。

**A 与 B 的差别落到代码只有映射方向一处**，但 service PR !291 现在按 A 落的
（`true→1`、派生 `==1`），**必须跟着改回**，否则两仓口径相反 —— 已在 #290/!291 留言。
