# 011 Todo 持久提醒调度

## 目标

任务提醒由操作系统持久调度，不依赖 App 进程内定时器；Android 设备重启或应用升级后仍能恢复尚未触发的提醒。

## 调度契约

- 提醒收件箱中的未来 `PENDING` 派发使用服务端 `dispatchId` 作为本地通知 ID，通过 `zonedSchedule` 交给操作系统调度。
- 已到期或 30 秒内到期的 `PENDING` 派发即时展示，保持现有前台轮询体验。
- 同一用户的派发 ID 和时间写入设备持久状态，只调度或展示一次；进程重启后仍保持幂等。提醒时间变化时使用同一通知 ID 覆盖旧调度。
- 派发不再是 `PENDING` 或从收件箱移除时，取消对应本地通知；App 重启后通过系统待调度请求恢复这组 ID，仍能清理已撤销派发。
- 通知 payload 与 Android tag 携带非敏感的租户/用户范围；系统待调度和活动通知只在当前范围内参与恢复与清理，避免账号切换时互相影响。
- 通知标题优先使用已同步的本地任务标题，其次使用派发携带的任务标题，最后回退为“提醒”。
- 调度失败不阻塞任务与同步流程，且不写入成功状态，下一轮继续重试。
- 设备状态写入失败会保留脏标记并在下一轮重试；系统待调度/活动通知作为异常退出窗口的恢复依据。
- 同一轮询器共享正在执行的请求，避免定时器与生命周期触发并发造成重复通知。

## 平台契约

- 初始化 `timezone` 数据后，以 UTC `TZDateTime` 调用系统定时通知能力。
- Android 使用 `inexactAllowWhileIdle`，不申请精确闹钟权限。
- Android 13 及以上通过插件申请通知运行时权限。
- Android Manifest 声明 `RECEIVE_BOOT_COMPLETED`，注册定时通知接收器与开机恢复接收器，处理设备启动、应用替换和厂商快速启动事件。

## 验收

- 自动化测试覆盖未来提醒持久调度、同 ID 改期、状态变化撤销、即时展示和 Android 重启恢复清单。
- `flutter analyze`、全量 `flutter test`、`flutter build web --release` 通过。
