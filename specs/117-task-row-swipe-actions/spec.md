## 之前的仓内状态

`lib/features/task/widgets/task_row_host.dart` 里那一行套的是一个 `Dismissible`：向右滑直接
`toggleComplete`、向左滑直接弹一张「更多」表。三件事与原文不符：

1. 形状不对 —— `:66` 写的是"出现了三个选项……点击对应的选项进行操作"，即**短滑露出、点击执行**；
   `Dismissible` 绑死的恰好是"滑到尽头即执行"，而且一个方向只能挂一个动作。
2. 档位不对 —— 左滑那一侧挂的是我们自己造的「更多」表（开始专注/删除/移动到清单/移动到分组/
   设置提醒/编辑标签），不是 `:66` 点名的那三件。
3. 那张表里有四颗是死按钮：删除、移动到清单、设置提醒、编辑标签 的 `onTap` 只做 `Navigator.pop`。
   本轮不动它们（另记 FL #601 评论），因为修它们属于那张表自己的面。

「移动任务」这一档**有既有通道，但它不在清单页**：侧栏拖放
（`lib/features/shell/sidebar_task_drop.dart:183`）与 `lib/features/task/list_drop_target.dart:107`
走的都是 `TaskRepository.update(taskId, listId: ..., clearSectionId: true)`，
批量「移至清单」走 `TaskBatchEditCommand(listId:)`。这三条都只改被点的那一行，
也都不校验目标清单是否可写。

## 需求与裁定

1. **形状：短滑露出 + 点击执行，两侧共用一个位移。**
   新组件 `lib/features/task/widgets/task_swipe_reveal.dart` 的 `TaskSwipeRevealRow`
   以像素位移驱动（`AnimationController.unbounded`），任一时刻只可能露出一侧
   （用例「一次滑动只可能露出一侧」把反方向拖过头那一步也量了）。
   方向命名跟 `DismissDirection`：`startToEndActions` = 手指向右拖 = `:71` 那一组，
   钮露在行的**左**边；`endToStartActions` = 手指向左拖 = `:66` 那一组，钮露在行的**右**边。
   两条用例分别按行的左右半区断位置，写反就会红。
2. **关闭态整条动作带根本不建。** 任务行的表面底色是透明的（选中/悬停色由外层给），
   按钮一直画着就会在静止时从行后面透出来 —— 这不是推测：第一版实现就是这么写的，
   黄金基线 `mobile-list` 当场红了 47.33%（155781px），改完 0 张红。
   复算：`flutter test --no-pub test/visual/todo_workspace_golden_test.dart`。
3. **档位是可跨设备记住的数据。** 落 `todo_view_preferences`
   （`sourceType='TASK_SWIPE'`、`sourceKey='global'`）+ `view_preference` 出箱，
   与「星期开始于」同一条通道 ⇒ 不升 `schemaVersion`、不加列。
   默认档就是 `:66`/`:71` 那两组，顺序照原文。
   复算（新文件未入库，判据必须带 `--untracked`，否则 `git grep` 会给出假的 0）：
   `git grep -c --untracked "TASK_SWIPE" -- lib` ⇒ 仓储那份文件 2 处；
   `git grep -c --untracked "TASK_SWIPE" -- test` ⇒ 用例那份文件 4 处。
4. **一侧上限 3（`maxActionsPerSide`）—— 这是本仓自己的布局取舍，不是原文的规定。**
   `:66` 的"三个选项"是在点名左滑默认那三件动作，`:71` 右滑默认只有两件，
   `:75` 也只说"可以进行自定义配置"，三处都没写过上限。
   取 3 的理由是窄屏：320px 上三块并排 216px，第四块就不是能点的东西了。
   仓储与设置页各挡一道：界面把第四个按不动，仓储拒重复与超限（直接调仓储的调用方也兜得住）。
5. **「移动任务」新造 `TaskRepository.moveToList`，与既有 `update(listId:, clearSectionId:)` 差三处。**
   一是子树跟着走：清单页已经把子级铺成行（`specs/116`），只挪父行会让子级留在原清单，
   展开箭头点开是空的。二是目标清单必须可写（旧通道不校验，挪进只读清单就是一行改不动的任务）。
   三是**子任务不单独换清单**：同文件 `_assertParentChainDoesNotContain` 要求父子同清单
   （抛「父任务必须属于同一清单」），只挪子行会当场造出那种状态 ⇒ `moveToList` 直接拒，
   界面在开表之前就挡并说"请随主任务一起移动"。
   清分组这一条**不是新账** —— 侧栏拖放早就写着 `clearSectionId: true`，本轮照同一口径。
   详情面板的清单切换、侧栏拖放、批量「移至清单」仍走旧通道 ⇒ 本轮不改，另立工单（见 tasks.md"后续"）。
   复算：`git grep -n --untracked "moveToList" -- lib/features/task lib/state/repositories` ⇒ 定义 1 处 + 行宿主调用 1 处。
6. **其余四档一律接既有通道，不新造写库路径。**
   完成 = `toggleComplete`、置顶 = `togglePin`、删除 = `delete`（它本来就带后代级联）、
   修改日期 = `TaskViewActionRepository.scheduleTaskToDay`
   （时刻/全天语义都不变，与日历拖动、「今天」清单落点同一条路）。
   失败提示统一走 `taskViewMutationFailureMessage`，只读清单的报错因此自动变成那句"只读"文案。
7. **文案跟着状态说真话。** 已完成那一行的完成档写「取消完成」、已置顶那行写「取消置顶」；
   用例断的是**那颗钮自己身上**的文字（行体别处也有"完成/取消完成"字样，全文找会撞）。
8. **露出态点行体只收起，不顺手选中任务。** 靠一张盖住行体的 barrier（钮在它之外，仍点得动）。
   收起态点行体照旧选中 —— 两条用例一起兜住"新组件没把既有点击吃掉"。

## 有意差异（不是缺口）

- **设置路径少一层。** `:75` 写的是「设置」-「更多设置」-「滑动操作」；本应用的设置页
  没有「更多设置」这一层，这一项直接落在「任务」分组里。名字与"可以进行自定义配置"照原文。
- **移动端行上的「更多」表入口随形状撤掉。** 行上原本只有左滑能开那张表；
  `:58` 把这一类入口放在任务详情页右上角「···」，而详情页确实有「开始专注」（`_compactMoreActions`），
  并且 `test/features/task/task_focus_entry_test.dart` 第二条用例已经在测它。
  ⚠️ 「移动到分组」全仓只有那张表里有 ⇒ 移动端从此没有这个入口（桌面端右键「更多操作」仍在）。
  镜像里没有这一档：在 zh-cloud-docs 仓执行 `git grep -rn "移动到分组" -- todo/99_参考资料`
  ⇒ 无输出（0 命中），它是我们自己加的。
  所以本轮按"不新增、也不顺手补"处理，恢复与否另立工单。
