## 取舍要写在台面上

1. **菜单项目前只有「分配给」一项。** 源页 `:175` 只写了这一条；清单行那个右键菜单里的「开始专注/更多操作」
   是 develop 既有形状，我没有把它搬进看板卡片 —— 把两套菜单合并会造出嘀嗒页面上没写的组合。
   代价：看板上右键能做的事比清单行少。将来若按其它面（如《09-桌面快捷操作》）补菜单项，要重新对照原文逐条判。
2. **动作收成一个共享函数，不复制两份。** `lib/features/task/task_assign_action.dart` 的
   `openTaskAssignAction(context, ref, task)` 由详情 Sheet 的「指派执行人」与看板卡片右键共用；
   详情页原来那段（读 `appDatabaseProvider` → `listByLocalId` → push `TaskAssignPage`，失败给可见提示）被替换成对它的一次调用。
   这是"复用不复制"，不是顺手重构：新入口必须做同一串前置校验，抄一份就会漂移。
3. **提示文案沿用 develop 原句**（「任务尚未同步，无法指派」「请先登录」「清单尚未同步，无法选择执行人」）。
   第三条在**收集箱任务上是错的** —— 见「本轮撞出来的一个既有缺陷」。
4. **key 放在条目根 widget 上。** `ReorderableListView` 要求每个条目根带 key
   （我把 key 挪到内层 `Padding` 时，测试直接炸出 `Every item of ReorderableListView must have a key.`），
   所以 `ValueKey('kanban-task-…')` 留在 `GestureDetector` 这一层，`Padding` 只是它的孩子。
   这条既有用例（`task_kanban_reorder_widget_test.dart`）靠同一个 key 定位卡片，形状不能改。
5. **窄屏的卡片是懒建的。** 320px + 1.3 倍字号时 `kanban-task-…` 根本没 build，
   所以辅助函数是"先滚到卡片、再断言它存在"，不是"先断言、再滚"。顺序反了就会得到一个假故障。

## 本轮撞出来的一个既有缺陷（有运行时证据，不是读码猜的）

收集箱任务（`listId == 'inbox'`，`todo_lists` 里**没有**这一行）走「分配给」时，
`openTaskAssignAction` 拿 `db.listByLocalId('inbox')` 得到 null，于是提示
**「清单尚未同步，无法选择执行人」** —— 而这条清单永远不会同步（它是虚拟入口）。
用例第 3 条（真清单：任务 + 清单都有 serverId ⇒ 真的 push 指派页）与第 4 条（收集箱 ⇒ 这句提示）
把两种情形分别钉住了，所以这不是推测。develop 的详情页「指派执行人」走的是同一段代码，
**同一条误导性文案在老路径上早就存在**；本 Issue 只新增了一个入口，没有新增机制。
⇒ 立 todo-flutter Issue **#318**：收集箱任务的指派要么按嘀嗒的口径给"收集箱不能指派/请先移到清单"这类准确说明，
要么按服务端能力判定；本轮不改（不顺手重构清单侧既有路径）。

  已经判定可达，但这不等于右键菜单该长什么样有完整对照 —— 帮助中心没写看板右键的完整菜单项，
  所以我不补别的项，也**不声称**"看板右键菜单已复刻"。
- 收集箱指派的正确文案（#318）。
