## 取舍要写在台面上

1. **菜单项目前只有「分配给」一项。** 源页 `:175` 只写了这一条；清单行那个右键菜单里的「开始专注/更多操作」
   是 develop 既有形状，我没有把它搬进看板卡片 —— 把两套菜单合并会造出嘀嗒页面上没写的组合。
   代价：看板上右键能做的事比清单行少。将来若按其它面（如《09-桌面快捷操作》）补菜单项，要重新对照原文逐条判。
2. **动作收成一个共享函数，但"行为一字未变"这句话我说过头了（第 1 轮复核抓到）。**
   详情页原来那段里，`await _resolveList(...)` 之后紧跟 `if (!mounted || widget.taskId != t.id) return;` ——
   这是我抄漏的一处**陈旧响应守卫**（Sheet 可以切任务，旧任务的指派页会盖到新任务上），而同函数的评论/成员分支仍然留着它。
   处置：`openTaskAssignAction` 收一个 `stillCurrent` 回调，详情页传 `() => mounted && widget.taskId == t.id`，
   守卫**回到原位**；看板卡片那条路不传（菜单在选中瞬间同步交出对象，没有跨 await 的旧响应可言）。
3. **提示文案沿用 develop 原句**（「任务尚未同步，无法指派」「请先登录」「清单尚未同步，无法选择执行人」）。
   其中「请先登录」这一支**没有用例**：它要求 `appDatabaseProvider` 为 null，而同一个 provider 又是页面渲染任务的前提，
   在这份 harness 里造不出"看得见卡片但库为 null"的状态 —— 记成结构性缺口，不假装测过。
4. **`onAssignCard` 是必填的。** 第一版我把它写成可空 + 两处判空，而 `_KanbanColumn` 是私有 widget、
   全仓只有 `KanbanView.build` 一处构造且传无条件闭包 ⇒ 那两处判空永远走不到，
   正是 specs/044 撤证里我批评过的"读起来防御、其实不可达"的死形状。改必填、删判空。
5. **key 放在条目根 widget 上。** `ReorderableListView` 要求每个条目根带 key
   （我把 key 挪到内层 `Padding` 时，测试直接炸出 `Every item of ReorderableListView must have a key.`），
   所以 `ValueKey('kanban-task-…')` 留在 `GestureDetector` 这一层，`Padding` 只是它的孩子。
   这条既有用例（`task_kanban_reorder_widget_test.dart`）靠同一个 key 定位卡片，形状不能改。
6. **窄屏的卡片是懒建的。** 320px + 1.3 倍字号时 `kanban-task-…` 根本没 build，
   所以辅助函数是"先滚到卡片、再断言它存在"，不是"先断言、再滚"。顺序反了就会得到一个假故障。

## 一条我自己立错、当天撤掉的 Issue（#318）

第 1 轮复核否掉了它的根因，我回源复验后确认**复核是对的**：

- 我的主张：收集箱 `listId == 'inbox'` 在 `todo_lists` 里没有行、`listByLocalId` 必返回 null、
  所以「清单尚未同步，无法选择执行人」是**永远不会实现**的误导性文案。
- 实况：`lib/core/sync/sync_coordinator.dart:119-134` 会在缺行时**插入** `id='inbox'` 这一行；
  `:145-158` 更有一段**专门**把这条清单的 upsert 塞进 outbox 的代码（`entity: SyncEntities.list, entityLocalId: 'inbox'`），
  `:839-856 _applyAccepted` 再 `_bindServerId(db.todoLists, …)` 把服务端 id 回写；
  pull 侧 `:1477-1497 _upsertLocalList`（`isInbox = payload['name']=='收集箱'`）把服务端行映射回本地 `'inbox'` 并写 `serverId`。
  `list_repository.dart:24/37` 的 `t.id.equals('inbox').not()` 只把收集箱从**清单选择器**里滤掉，不阻止它同步。
- ⇒ 存在一条"就是为了给收集箱拿到 serverId"的链路，"永远不会同步"被直接否证。**#318 撤销关闭**。
  用例第 4 条观察到的那句提示是真的，但它的成因是"这份 fixture 没给收集箱建行"（= 未同步态），
  而不是"收集箱不可能同步"；该用例已改成用**工作清单**演"本地清单尚未同步"这种生产里真会发生的情形，
  不再拿收集箱当道具。
- 教训（和我在 specs/044 里刚写过的那条同源）：**grep 到"某处判空"就宣布缺陷，缺的是把整条链读完**。
