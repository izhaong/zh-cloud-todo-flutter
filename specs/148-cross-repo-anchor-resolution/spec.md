# 148 · 跨仓锚点可解析（原 FL #394）

## 现象

`tool/check_spec_selfscan.py` 的死锚点判据只在**本仓**三处查
（`resolve()` 的绝对路径 / 仓根、`bare_matches()` 的 `git ls-files`）。
于是一条指向**另一个仓**的**真实**引用结构上永远解析不到 ⇒ 被判「死锚点等于没证据」。

误伤的后果比漏报更糟：写台账的人会去删**真证据**来让它变绿（脚本 docstring 里第 8 轮复核 F12
记的正是这个失败模式）。

## 内容（原单四条要求，逐条落地）

| # | 要求 | 落地 |
| --- | --- | --- |
| 1 | 认 `<repo>/<path>:<line>` 与 `<repo>@<ref>:<path>:<line>`；`<repo>` 按兄弟目录解析；取对象用 `git -C <sibling>`；**显式标基准 ref**；解析不到才判死 | 新增 `CROSS_AT` 正则 + `sibling_repo_root()` + `cross_blob_lines()`。**基准 ref 的规则写死**：写了 `@ref` 就按它（并试 `origin/<ref>`，与 `branch_blob_lines` 同口径）；没写就按该仓集成线 `origin/develop` → `develop` → `HEAD` → 最后才回落到工作树文件。顺序是「规范 ref 优先」，免得同一份台账在「有 worktree」和「只有克隆」的机器上给出两个数 |
| 2 | 缺兄弟仓判 **error** | 首段匹配 `zh-cloud-*` 而兄弟仓不在 ⇒ **判红**并写明判据命令。设这条前缀是为了不误伤普通相对路径（例如 `lib/features/` 下某个文件的行号引用，其首段 `lib` 不是仓名） |
| 3 | 打印分类计数 | 每次运行打一行：`本仓可比对 / 跨仓可比对 / 跨仓缺兄弟仓（判红）/ 判成不成立`。豁免不计数就会变成免死金牌 |
| 4 | `--selftest` 加变异：把跨仓锚点的仓名去掉 ⇒ 必须变红 | 新增一对**成对**语料：带仓名绿、去掉仓名红。同一份内容，只有仓名之差 ⇒ 证明新判据有判别力、不是恒绿 |

## 顺带修掉两个真问题

1. **`BRANCH_REF` 迭代的是 `line` 而不是 `scan`**：它不尊重前面几趟打过的码。
   以前它跑在第一个，所以没暴露；`CROSS_AT` 前置之后就现形了 ——
   `仓@ref:路径:行` 会被 `BRANCH_REF` 再当成 `ref:路径:行` 判一次。
   是新增的 `@ref` 语料把它抓出来的（期望绿、实际红）。
2. **`.sql` 锚点原本被静默跳过**：死锚点判据只在 `re.search(r"\.(log|md|dart|txt|py)$", raw)`
   成立时才报。跨仓分支不受这条白名单限制 ⇒ 现在 `zh-cloud-service/sql/…:334` 这种
   跨仓 `.sql` 引用**真的被查**（分类计数里记成「跨仓可比对」），而不是装作看不见。

## 加了一个 `ZH_CLOUD_ROOT` 口子（非原单要求，但不加就没法在非标准布局里用）

原单假定兄弟仓在 `../<repo>`。但本工作区是 `todo-worktrees/{todo-flutter,todo-service,…}`，
兄弟仓的名字根本不是 `zh-cloud-*` ⇒ 在新判据下**每一条跨仓锚点都会判红**（这正是要求 2 的行为，
但也意味着这个工具在这些布局里跑不出有意义的读数）。

故 `sibling_repo_root()` 先看 `../<name>`，再看 `$ZH_CLOUD_ROOT/<name>`
（同 `zh-cloud-docs/scripts/todo/check_parity_matrix.py` 的既有先例）。两处都没有才判红 ——
**没有把「找不到」放宽成「跳过」**。
