# 159 · 「挪到某一天」时**时段跟着一起挪**（原 FL #584）

## 病灶

改「哪一天」的三条入口（`moveCalendarTask` / `addToToday` / `scheduleTaskToDay`）都**只写 `dueAt`**，
不动 `startAt`/`endAt`。于是一条有起止时段的任务被挪日子之后：

- 按 `dueAt` 过滤的清单（今天 / 明天 / 最近七天）说它在**新的一天**；
- 按 `startAt` 分桶的时间线与日历把它画在**原日**。

两处各说各话。这条约定还被一条用例**成文钉着**（`task_view_action_repository_test.dart`
「…时段留在原日（与日历拖拽改期同口径）」），而那条 reason 里自己写着
「跨三处的修法**另开单**」—— **本单就是那一单**。

## 改动

三条入口共用一个**整天平移** helper：把时段按"**它自己的展示日** → 目标日"的日历日差平移，
**时段长度与钟点都不变**（用年月日重新构造，不用 `add(Duration)` —— 跨夏令时那天后者会把钟点挪掉一小时）。

**参照物是「时段自己的展示日」，不是截止日**：种子里就有"时段与截止日本来不在同一天"的记录，
用截止日的差值会把它挪到第三个日子上去（判据当场抓到：时段落到 2027-02-28，而截止日在 2026-10-20）。

## 判据

| 判据 | 说明 |
| --- | --- |
| 挪完之后**时段与截止日落在同一个展示日** | 这是本单要修的那件事本身 |
| **时段长度不变** | 整天平移，不该改时长 |
| 既有那条"只更新截止时间"的用例改成新口径 | 它的 reason 里写明"这条口径变了、为什么" |

**断言不变量而不是写死日期**：换个种子就得重算，而这条判据真正要守的是"同一天"。

## 两处判据抓到的**我自己写的 bug**（都不是判据错，是实现错）

1. **`_shiftWallClockByDays` 把 UTC 的 `DateTime` 重建成 local** ⇒ 瞬间被平移一个时区偏移
   （判据：时段落在 2027-02-28 而截止日在 2026-10-20）；
2. **参照物取错**（用截止日的差值而不是时段自己的展示日）⇒ 时段被挪到第三个日子。

两处都是**判据先红、我才发现的**。如果我只跑"绿了就提交"，这两处都会进主干。

## 边界

- **不含** #587（跨午夜时"这一天是哪个时区的天"）与 #312（服务端拿不到用户时区）——
  那两件要产品定口径，方案已写在 #587 的评论里（A/B 两条路 + 推荐 A）；
- 本单**不依赖**那两个选择：无论选哪个，时段都不该留在原日。
