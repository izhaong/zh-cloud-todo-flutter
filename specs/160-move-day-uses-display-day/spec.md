# 160 · 「挪到某一天」的落点日取**展示侧**日历日（原 FL #587）

## 病灶

`taskDateTimeForDisplayDay`（日历拖拽 / 时间线拖动 / 智能清单落点**共用这一个 helper**）
对「固定时区」档（`time_mode = 1`）取的是**锚点区**的日历日，而**所有读侧**（智能清单 /
日历 / 时间线 / 筛选用例）都读**展示侧**。两者跨午夜时：

- 锚点 LA 18:30 → 设备（上海）次日 01:30；
- 用户把任务拖到日历「10-13」那一格 ⇒ 展示出来落在 **10-14**，**任务不出现在刚拖上去的那一天**。

## 订正依据（那一档**自己的原文**）

《02-功能指南/01-任务/07-固定时间与固定时区.md》：

> `:47` 选择「固定时区」，即意味着任务的**时间会随着所在时区的不同而改变**。
> `:49` 示例 1：如果你从北京飞到莫斯科，那么北京时间上午 11 点的任务，
>       将会显示为**莫斯科时间上午 6 点**。

⇒ 「固定时区」承诺的是**瞬间钉住、钟点随时区漂**。而"挪到某一天"是用户对着日历
说"**我要它在这一格**"。两者不冲突：钟点照旧漂（那是展示侧的事），但**落点日必须是那一格**。

> 我最初在 #587 里推荐的是相反的 A（保锚点墙钟），**核原文后自己否掉了** ——
> A 会把漂移钉死，与 `:47` 直接冲突。

## 改动

`taskDateTimeForDisplayDay` 改成：**基准取 `taskDisplayDateTime`**（展示侧），
目标瞬间 = 「`day` + 展示侧钟点」。

**三条不变量**（opencode 交叉验证后写死）：

1. **基准取展示侧，不是写死"设备当地"** —— mode 2（固定时间）的展示侧**就是锚点区**，
   写死设备当地会把"钟点钉死"一起破。这是交叉验证指出的**头号陷阱**；
2. 钟点不因挪日而变；
3. **返回类型契约不变**：展示侧 == 设备当地时（mode 0 / mode 1）返回**本地** `DateTime`
   （与改动前 `taskDateTimeFromWallClock` 在 `location == null` 时的行为一致）。

## 判据

| 判据 | 说明 |
| --- | --- |
| **扫全天 24 个钟点**，锚点区 `10-01 h:30` 挪到 `10-13` ⇒ 展示日**都是 13 号** | 只测一个钟点时，跑测试那台机器若不跨午夜就测不出差异 |

**为什么必须扫全天**：第一版只测 `09:30`，**反向探针跑完全绿** —— 本机 UTC-4 下两种口径
恰好都得 13 号，**判据没有区分力**。改成扫全天之后探针才红（落到 14 号）。

**反向探针**：把基准退回锚点区 ⇒ 判据转红（`Expected [2026,10,13]` / `Actual [2026,10,14]`）。

## 连带影响（本切片已一并验证）

改动落在**共用 helper** 上，所以日历 / 时间线 / 清单落点三个入口一起变。
既有 8 条以旧口径钉着的用例在改后**全部仍然绿** —— 因为按上面第 1、3 条不变量，
mode 0 / mode 2 逐字节未变，mode 1 只在跨午夜时行为改变（那正是要修的）。

## 边界

- **不含** #312（服务端拿不到用户时区）：提醒触发那半仍在服务端；
- **不含**重复规则序列锚点（`dueAt` 常被当 DTSTART）：跨午夜拖动会平移序列锚，
  需另核服务端 occurrences 口径（已记在 #587）。
