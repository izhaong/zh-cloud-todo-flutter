# 046 嵌入态任务详情操作头的窄面板折叠 — 规格

Issue **#279**（存量治理）。判据源：嘀嗒《01-任务/02-任务详情.md》（`zh-cloud-docs` develop 镜像
`todo/99_参考资料/dida365-help-center/02-功能指南/01-任务/02-任务详情.md`，**全页 405 行**），
以及本轮实测出来的**溢出量与字号无关**这一条（推翻 Issue 标题里的归因）。

## 实测：溢出的真实条件（先把病根说清，别照抄 Issue 的标题）

探针（临时测试文件，跑完删除）在 `_buildEmbedded` 的操作头上量；下表这四档里，**320/355/356/390 × 1.0/1.3 八格与
"一枚图标 48dp"这个数现在都由随 PR 提交的用例逐格钉住**（`test/features/task/embedded_detail_header_narrow_test.dart`，
每格一条 `testWidgets`，见「四件套」第一段），不再只是探针的一次性读数：

| 面板宽 | 字号 1.0 | 字号 1.3 |
| ----- | -------- | -------- |
| 320 | `RenderFlex overflowed by 36 pixels on the right` | **同样 36px** |
| 355 | `overflowed by 1.00 pixels` | 同样 1.00px |
| 356 | 无 | 无 |
| 390 / 760 | 无 | 无 |

- 7 枚 `IconButton` 各占 **48dp**（实测 `getSize().width` 全是 48.0）⇒ 336 + 4 间距 + 左右内边距 16 = **356dp** 是硬下限。
  写成比较用的常量时是**内容宽 340**（那 16dp 由包裹的 `Padding` 付，`LayoutBuilder` 给的 `maxWidth` 已扣掉）。
- 标题在 `Expanded` 里，被压到 0 也不会再省出空间 ⇒ **字号不参与**：`1.3` 与 `1.0` 的溢出量逐像素相同。
- ⇒ Issue #279 标题写的「320px + 1.3 倍字体下溢出」在**条件上归因错了**（真实条件是"面板 < 356dp"，
  320px 只是第一个撞上的宽度）。这条要留在 Issue 评论里，不是本文件的私货。

## 判定：折叠哪两项，为什么是这两项

嘀嗒《任务详情》把次要动作收在右上角「...」里（**"破坏性"是我的归类，原文没这个词**；原文只给了下面三句的入口形状），原话（逐字）：

- `:372`「进入任务详情页，点击右上角「...」-「更多」「任务动态」，就可以查看任务的历史修改信息。」
- `:391`「进入任务详情页，点击右上角「...」-「开始专注」，在专注窗口选择时间并「开始番茄专注」。」
- `:399`「在任务详情页或者弹窗中点击右上角「...」-「更多」，找到左下角「编辑」即可自定义任务详情操作菜单。」

⇒ "详情头部只放少数高频动作，其余进「...」"是嘀嗒自己的形状，不是我为省像素发明的交互。
本端整页态窄屏**早就这么做了**（`task_detail_pane.dart` 的 `_buildPage` 在 `narrow` 分支里把
「移至收集箱」「放弃任务」「协作」「删除」全列进 `PopupMenuItem`），嵌入态是唯一没跟上的那条路径。

折叠哪两项的取舍：**「移至收集箱」+「删除」**。
- 保留在栏上的 5 枚（关闭 / 置顶 / 勾选完成 / 协作 / 「...」）是"看这条任务时几乎每次都会用"的动作；
- 「移至收集箱」与「删除」都是**离开型**动作（做完就离开这条任务），且「删除」是破坏性的 —— 收进菜单反而降低误触；
- 折叠后固定宽度 `5×48 + 4 + 16 = 260 ≤ 320`，320px 有余量 60dp。

## 为什么不"直接改成 5 枚图标"（无条件折叠）

无条件折叠会让 **9 张黄金基线里的 2 张**（`wide-selected`、`compact-selected`）变样 ——
本轮实测跑过：把两枚图标无条件摘掉后 `flutter test --tags golden` 报
`Failing tests: compact-selected / wide-selected`（其余 7 张绿）。
重录基线属于"必须先问"的动作，而这里**有更小的做法**：
按 `LayoutBuilder` 给到的**面板实际宽度**决定折不折，宽度本来就够的场合一字不变
⇒ 门禁 4 在**不重录任何基线**的前提下 9 张全绿。

阈值写成常量 `_embeddedActionRowContentMinWidth = 340`。这个数**比较的是内容宽，不是面板宽**：
`LayoutBuilder` 在 `Padding(horizontal: 8)` 里面，`constraints.maxWidth` 已经扣掉了那 16dp，
所以 340 对应面板 356（实测 355 溢 1px、356 刚好）。第一版我把它写成 `_embeddedActionRowMinWidth = 356`，
**等于把同一份 padding 数了两遍**，真实折叠线被推到面板 372 —— 356~371 这一带会白折一次。
第 1 轮复核没抓到这条，是我自己按复核提的 density 那条去核对公式时发现的；
现在的折叠线由 `355 折 / 356 不折` 两档用例钉住（反向探针 PL：把常量改回 356 →
**恰好 `356.0 + 1.0` 与 `356.0 + 1.3` 两格红**，其余 11 条仍绿；320/355 本来就折，所以 PL 只惩罚这一带）。

## 取舍要写在台面上

1. **两套形状。** 折叠引入了"同一面板在不同宽度下动作位置不同"。这是**有意的**（保住基线 + 修掉溢出），
   代价是"删除在宽面板上看得见、窄面板上要按「...」"。反向证据由 `嵌入态宽面板不折叠…` 那条用例钉住，
   不是靠"反正没人测"。
2. **`foldedActions` 参数是必填的**，不给默认值：默认值会让"忘记判断"变成一条安静的错路。
3. **阈值不做成可配置项。** 它是布局常量而不是产品参数，配了也没人调。
4. **`LayoutBuilder` 的包裹让整块 `Row` 多一级缩进**（`--stat` 89/51 vs `-w` 40/2）。
   这不是"顺手格式化"，是嵌套层数的必然代价；核对方式已写进 `tasks.md` 的门禁 2b。
   如果复核认为该避免，可改成把操作头抽成独立方法 —— 但那会把整段搬家，读起来 diff 更大而不是更小。
5. **没顺手改的事**：整页态宽屏（`_buildPage` 的 8 枚图标）在极窄时同样会挤 —— 但 `AppBar.actions` 有自己的排版路径，
   本轮没有它的溢出证据，故**不动**（见「仍缺」）。
6. **`_TaskDetailAction.moveToInbox` / `.delete` 之前是"枚举里有、菜单里没有、handler 走 default 静默 return"**
   —— 也就是两个死的枚举值。本轮不是"清理死代码"，而是把它们接到真正会走到的分支上（折叠态需要它们）。
   顺带说明：`default: return;` 仍在，因为整页态菜单用的是另一串值（`copy`/`share`/`abandon` 等在 `_buildPage` 内联处理）。
7. **复核提的"阈值该随主题 density 算"，我试过并且驳回了（这条记成书面理由）。**
   复核的推理是 `ThemeData` 用 `adaptivePlatformDensity`，桌面/Web 是紧凑档 ⇒ 图标 40dp ⇒ 写死会让 300~355dp 白折。
   我照它改成 `48 + visualDensity.horizontal * 4` 跑了一遍：**紧凑主题下面板 300dp 直接溢出 56px**
   （= 7×48+4 − 内容 284），也就是图标压根没缩。回源看：本仓主题 `useMaterial3: true`
   （`lib/app.dart:109`、`:150`），而 M3 的 `IconButton` 把样式里的 `visualDensity` 硬编成 standard
   （SDK `material/icon_button.dart:1152`、`:1294`、`:1436`、`:1573` 四个 getter），
   `ThemeData.visualDensity` 走不到这几枚按钮 —— 只有 M2 的 legacy 分支（`icon_button.dart:779`）才读它。
   所以阈值留在 340，并加一条用例把"紧凑密度下仍折、图标仍 48dp"钉住；
   如果哪天 M3 改成跟随密度，那条用例会先红，届时按新读数重算，而不是照抄 40。

## 四件套（改了可见表面）

| 件 | 判据 | 读数 |
| -- | ---- | ---- |
| 320px + 1.3 倍字号（在面板自己的 context 上量） | `LayoutBuilder` 拿的是**面板宽度**，不是屏幕宽度；320/355/356/390 × 1.0/1.3 八种组合**各一条 `testWidgets`**（合成一个循环的话 `takeException()` 只吐第一条，后 7 格红不了） | 八条用例：逐格 `headerChildrenExtent ≤ 内容宽` + `takeException()` 为 null + 该格的折叠状态（`356` 为界）与图标 48dp 读数 |
| 独立读屏语义 | `tester.ensureSemantics()` 后读菜单项 | 用例 `挪进菜单的两项各自有读屏语义…`：`移至收集箱`/`删除` 的 label 各自含其文；栏上 4 枚 tooltip（关闭详情/置顶/勾选完成/协作…）各 `findsOneWidget` |
| 失败保留已加载数据 | 「删除」仍走 `AppDialog.confirm`，取消后逐列比对 | 用例 `「移至收集箱」与「删除」收在「更多任务操作」里…`：取消后 `afterCancel.toJson() == before.toJson()`（整行 26 列），且 `listId` 未变 |
| 过期响应不覆盖新响应 | 菜单项在选中瞬间交出**当时那条任务对象**（`_onCompactMoreAction(t, …)` 的 `t` 来自 build 入参），本轮没引入任何跨 await 的列表状态 | 结构判据（**没有独立用例**：折叠态的关闭语义已由上面那条的 `_close()` 覆盖，跨任务切换的时序不在本轮改动路径上） |

量法说明（第 1 轮复核抓到的一处假断言）：第一版用 `getSize(row).width ≤ 面板宽`，**恒真** ——
溢出那一帧 `RenderFlex` 的 size 仍是被约束夹住的 304，而孩子已经画到 340。
现在量的是每个孩子 `parentData.offset.dx + size.width` 的最大值 vs `flex.size.width`，
反向探针 PM（把阈值改成 0 = 永不折叠）读到 `Expected: ≤ <304.0> Actual: <340.0>`、
`Expected: ≤ <339.0> Actual: <340.0>` ⇒ 这条断言真的会红，且能报出 1px 那一档。


## 仍缺（不谎称完成）

- 折叠阈值只在**嵌入态**生效；整页态 `_buildPage` 的图标栏没有"宽度不够就折"的等价逻辑（缺溢出证据，未动）。
- 「触屏端右键/长按能否等价到达折叠掉的两个动作」没判 —— 这属矩阵 #15 那条线（**`specs/045-kanban-card-assign` 目前只在 PR !319 的分支上，`origin/develop` 到 044 为止**），不混进本轮。
- 嘀嗒《任务详情》`:399` 的**「自定义任务详情操作菜单」（「编辑」+「+/-」置顶 + 拖拽排序）**整面仍无 ——
  本端折叠是**写死的两项**，不是用户可编辑的。这属矩阵里"详情操作菜单可自定义"那一格，本轮不声称覆盖。
