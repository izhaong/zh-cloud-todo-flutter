# 成就墙导航入口（设置/我的 → 成就与勋章）

对齐矩阵 #76–78「成就值与勋章（父）·成就值·勋章」。#76、#77、#78 各行逐条的结论见 `zh-cloud-docs` 矩阵主表；实现链早已齐备，唯一缺口是
**用户可达性**：矩阵原判「实现链齐但没有任何导航入口」。

## 嘀嗒口径（先读了对应那一页）

- `10-成就值与勋章/01-成就值.md`：成就值是**统计族**的内容（「丰富了统计的内容，并引入成就值来展示结果」），
  且「成就值并非实时更新，滴答清单会于每天凌晨 00:00 更新成就值」。
- 术语沿用嘀嗒原文：「成就值」「成就等级」「勋章」；不自造同义词。
- 专注统计在本仓已另有落点（`features/pomodoro/pomodoro_page.dart` 的「专注统计」区），
  所以成就的顶层入口只需一个**能一次点击到达、且语义不拧巴**的位置。

## 现状（实地证据，2026-09-23，本分支基线 = develop `a1d7733`）

- 链路齐：`lib/core/api/efficiency_api.dart` `AchievementApi` → `:948` `GET /achievement/wall`
  → DTO `:327`（勋章）/`:353`（墙）→ `lib/state/efficiency_providers.dart`（api）/`:63`（wall provider）
  → 页面 `lib/features/achievement/achievement_page.dart` → 既有测试 `test/achievement_page_test.dart`。
- 但 `grep -rn "AchievementPage" lib` 在改动前只命中页面自身与
  `lib/features/efficiency/efficiency_hub_page.dart`，而 hub 自身无任何调用点 ⇒ 成就对用户不可达。

## 为什么不采用 specs/027 的「hub 接线」路线（重要，避免下一轮又试一遍）

specs/027（在 `chore/todo-visual-harness-overrides` / PR !269 上，未合并）试过把侧栏 dock 的三个入口
改推 `EfficiencyHubPage(initialIndex:)`，切片用例与六项门禁当时都绿，但只读复核判 **FAIL** 后整体回滚。
本轮开工前复核了「子页嵌入态」这条前置路的真实代价，结论是**代价与收益不匹配**：

- hub 自带一个 `AppBar`，四个子页**各带一个**，且各子页的动作都挂在各自 `AppBar` 上：
  `habit_page.dart:18`（新建）、`countdown_page.dart:14`（新建）、
  `pomodoro_page.dart:1124-1190`（归档视图切换、新增常用专注、含「进入沉浸模式/自动进入/屏幕常亮/三种计时样式」的弹出菜单）、
  `achievement_page.dart:17`（无动作）。
  ⇒ 「嵌入态」= 同时重写 4 个**已验收**表面的 chrome，并给 hub 加一套按页签切换动作区；
- 沉浸专注还要求 hub 在子页进入全屏时收掉自己的 `AppBar`（跨层通知），否则会剥夺已验收的全屏体验。

因此本切片改走**不触碰任何已验收视觉**的路线：把成就放进「设置」页（即本仓的「我的」聚合页）。
它有两条 push 点，都在 `lib/features/home/home_shell.dart`：`:457` `_openSettings()`（宽屏侧栏「设置」行）
与 `:828-831` 抽屉里的「设置」`ListTile`（窄屏），两条都进同一个 `SettingsRoute`。该页已经是各类
非设置目的地的宿主（账户安全 / 日历订阅 / 任务导入 / 原生增强），成就与它同族，且它**不在**
`specs/002-todo-visual-fidelity` 已批准的 9 张黄金图内 ⇒ 零基线影响
（严格说：矩阵原话「push 路由零视觉覆盖」只对 8/9 成立，`mobile-detail` 那一例会 tap 进
`TaskDetailPage` 再拍图；这与本切片无关，已在矩阵侧另行更正）。

## 功能需求

- **FR-001** 「设置」页「账号」分组内提供「成就与勋章」行，一次点击直达既有 `AchievementPage`
  （不新建页面、不复制一份成就 UI、不绕道未被采用的 hub）。
- **FR-002** 行的副标题必须把「成就值每天凌晨更新」这一口径带到脸上（嘀嗒原文口径），
  而不是只写一个名字。
- **FR-003** 成就墙拉取失败时，经该入口进入后仍是既有的失败态 + 可重试，重试成功后显示数据。
- **FR-004** 320px 宽 + 1.3 倍字体下入口仍在树里、可滚动到、可点击、无 RenderFlex 溢出；
  字体档位必须真正传到 push 出来的成就页（用弹层/路由 context 自检，不用外部探针）。
- **FR-005** 读屏能读出该入口的**名称与更新口径**：实测 `ListTile` 把 `title` 与 `subtitle` 合成
  可聚焦节点：label 里名称打头、口径在后，所以本条钉的是「同一节点内两者都在、名称打头、
  不靠颜色或图标传达」；「两条文案各自成为独立节点」在本仓组件上不成立，用例按实测写。
- **FR-006** 侧栏 dock 的视觉与文案零改动 ⇒ 不触碰 9 张黄金图基线。

## 边界与非目标

- 「dock 加第 4 个成就按钮」不在本轮：那会改动侧栏可见区域、需要重录 9 张基线（未获授权），
  留作后续申请项。
- `features/efficiency/efficiency_hub_page.dart` 本切片**不接线也不删除**：它是 develop 上既有的无调用点页面，
  删除属顺手重构，接线属上面那条已被否决的路线。它的归属留给 specs/027 的结论。
- 成就值的服务端计算规则、勋章发放（后端已实现）、等级曲线调整均不在本切片范围。
- **与旧规格的措辞冲突已在本切片收口**：`specs/001-todo-dida-core-parity/spec.md` 的验收场景原写
  「打开**效率中心的成就勋章页签**」，那是 hub 路线的措辞，而 hub 路线按复核结论未采纳
  （四个子页的动作都挂在各自 `AppBar` 上，嵌入态等于重写四个已验收表面）。001 那句已改为
  「打开设置页「账号」分组的「成就与勋章」」——即本切片实装的入口与已交付的页面标题。
  若将来 hub 路线（含基线重录）获批，另开规格变更，不再回改本切片。
